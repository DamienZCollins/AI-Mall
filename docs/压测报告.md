# 秒杀压测报告

> 目的：用真实数据量化「Redis 预扣 + RocketMQ 异步下单」相对「数据库同步下单」的收益，并定位瓶颈。
> 结论先行：**售罄后流量场景异步版吞吐为同步版 2.7~2.8 倍，P99 降 54%**；
> 突发抢购场景入口延迟降 18%~47%（随客户端配置不同），P99 持平。
>
> 本报告汇总两轮压测，两轮数据均完整保留：
> - **A 轮（2026-10-14）**：修复压测客户端三大坑之后的完整对照，含虚拟线程实验，数据见 3.2 与 3.4 节。原始 `.jtl` 未随仓库保留。
> - **B 轮（2026-10-20）**：统一 200 线程、多轮取中位数的复跑，数据见 3.1 节。原始 `.jtl` 保留在 `backend/scripts/loadtest/results/`，可复算。
>
> 对外口径使用 B 轮数字（可复算），A 轮作为方法论与瓶颈分析依据。

## 1. 测试环境

| 项 | 配置 |
| --- | --- |
| 主机 | Windows 11，32 逻辑核，32 GB 内存 |
| Docker 资源 | 8 CPU / 7.76 GB |
| 应用版本 A（同步） | `0cd8aed`（最后一个纯数据库同步下单提交），独立 worktree，`java -jar` |
| 应用版本 B（异步） | `main`，Redis Lua 预扣 + RocketMQ 异步落库 |
| 虚拟线程 | `spring.threads.virtual.enabled=true`，对照时用命令行参数覆盖 |
| 中间件 | MySQL 8.4、Redis 7.2、RocketMQ 5.3.2，均单机容器 |

| 连接池 | Hikari 默认上限 10（两版一致） |

两个版本连同一套 MySQL / Redis / RocketMQ，串行压测，压测期间只有一个应用进程在跑。

## 2. 测试方法

### 2.1 基线 worktree

同步版本的代码已从 `main` 移除，用 `git worktree add ../Mall-sync 0cd8aed` 拉出。
该提交的 `sql/schema.sql` 与当前完全一致，可直接连同一套库。

### 2.2 账号与令牌

- A 轮 4000 个压测账号（`load201`..`load3200`，密码统一 `user123`）；B 轮 300 个（`load001`..`load300`）
- 令牌在压测前 `setUp` 阶段一次性登录取好写入 CSV，避免 BCrypt 校验占用压测时长
- 每档位结束后重置活动、订单与 Redis 状态，保证两个版本从同一初始状态出发

### 2.3 预热处理

异步版库存在首个请求时按需预热，直接压测会把重建开销算进请求延迟：
未预热时异步版平均延迟 1601 ms，预热后降到 101 ms，差异全部来自预热本身。
压测前用不参与压测的账号触发预热，再把订单、库存和 Redis 状态还原。

### 2.4 压测工具的四个坑（都会静默扭曲结果）

1. **`boolProp` 不做属性替换**。`<boolProp>` 只认字面 `true/false`，`${__P(...)}` 被当成 false。
   最初的 `use_keepalive` 和 `scheduler` 都因此失效——keep-alive 关闭导致每请求新建连接，
   2 万多个 TIME_WAIT 耗尽端口，大量 `SocketException` / `BindException`。
   这类错误发生在**客户端建连阶段**，服务端日志干净，极易误判为被测系统的问题。
2. **HTTP 实现的选择**。HttpClient4 在 Windows 上建连速率明显低于 Java 实现：
   同样 200 并发，HttpClient4 报 47.5% SocketException，Java 实现零错误。
3. **单循环压测测的是爬坡不是吞吐**。线程数等于样本数时，QPS = 线程数 / 爬坡时间，
   与系统处理能力无关。持续压测必须 `loops=-1` 配合调度器（调度器同样受坑 1 影响）。
4. **残留 JMeter 进程**。上一轮被中断的进程仍在打请求，TIME_WAIT 长期不降；
   杀进程后 TIME_WAIT 从 23651 降到 140。

判定错误归属的方法：用同样并发打一个零业务接口（`/actuator/health`），
若同样报错则是客户端问题。本次靠这个对照实验定位根因。

### 2.5 场景定义（两轮一致）

- **T1 突发抢购**：库存 100，300 个账号预取令牌，全部线程在 1s 爬坡内同时打
  `POST /api/seckill/{activityId}`。
- **T3 售罄后流量**：先用 150 个账号把 100 件库存抢空，再用 200 线程持续打 30s，
  全部返回售罄。这是秒杀的真实形态：售罄请求不改变任何状态，可重复打，不会耗尽账号。
- B 轮异步版每笔成功请求轮询 `/result` 直到 `SUCCESS`，轮询开销单记在「抢购全链路」，
  不混入 POST 延迟。

## 3. 测试结果

### 3.1 B 轮（简历口径，200 线程，中位数：T1 5 次 / T3 4~5 次）

| 指标 | 同步版 | 异步版 | 变化 |
| --- | --- | --- | --- |
| T3 售罄后吞吐 | 671 QPS | 1,829 QPS | **2.7×** |
| T3 售罄后 P99 | 472 ms | 217 ms | **−54%** |
| T1 突发抢购 POST 平均 | 404 ms | 333 ms | −18% |
| T1 突发抢购 POST P99 | 641 ms | 642 ms | 持平 |

原始区间：

| 场景 | 版本 | QPS 区间 | P99 区间 |
| --- | --- | --- | --- |
| T3 | sync | 573–779 | 391–641 |
| T3 | async | 1,332–1,857 | 215–330 |
| T1 | sync | 344–448 | 508–711 |
| T1 | async | 364–488 | 488–788 |

含轮询的全链路（异步版的真实代价）：

| 版本 | 全链路平均（中位） | 全链路 P99 |
| --- | --- | --- |
| 同步 | 490 ms | 918 ms |
| 异步 | 861 ms | 1,612 ms |

客户端封顶验证：B 轮 400 / 600 线程时两版都撞到约 1,700 QPS 的客户端上限
（`t3-*-t400/t600.jtl`，且 600 线程出现客户端 `SocketException`），
故统一取 200 线程对比；异步版 T3 单轮最高瞬时 2,044 QPS（warm 轮）。
Windows 下突发建连偶发 `Permission denied: connect`，已通过 JMeter 重试与连接超时
配置消除，仍以中位数为准。

### 3.2 A 轮（2026-10-14，修复客户端问题后的首轮完整对照）

T1 突发抢购（库存 100 / 400 并发 / 1s 爬坡）：

| 版本 | QPS（三次） | 平均延迟 | P99 范围 |
| --- | --- | --- | --- |
| 同步 | 483.1 / 471.7 / 448.4 | 212.5 ms | 382–523 ms |
| 异步 | 446.4 / 430.6 / 438.1 | 111.8 ms | 367–447 ms |

T3 售罄后流量（库存 100 / 200 并发 / 30s）：

| 版本 | 样本数 | QPS | 平均 | P95 | P99 |
| --- | --- | --- | --- | --- | --- |
| 同步 | 26,613 | 891.3 | 206.2 ms | 310 ms | 339 ms |
| 异步 | 73,262 | 2,464.1 | 74.6 ms | 97 ms | 157 ms |

**两轮倍数一致（T3 吞吐 2.76× vs 2.7×，P99 −54%），绝对值差异来自客户端配置与
账号池规模不同，跨轮绝对值不可直接比较，轮内比值才可信。**

### 3.3 正确性核对

两个版本、每一轮结束后核对结果一致：

```text
orders=100  distinct_users=100  duplicate_orders=0
db_stock=0  oversold=0  redis_stock=0  redis_matches_db=true
```

### 3.4 虚拟线程：搜索接口尾延迟对比（A 轮）

秒杀接口在 Redis 层就被拦下，几乎不阻塞，虚拟线程在这里没有收益空间
（售罄档位开关虚拟线程均为 2,100–2,460 QPS，差异在噪声内）。

搜索接口每次请求要调一次 embedding 接口（约 750 ms），是典型阻塞场景。
同一个 jar、只改 `spring.threads.virtual.enabled`，400 并发持续 40s：

| 线程模型 | p50 | p95 | p99 | max | p99/p50 |
| --- | --- | --- | --- | --- | --- |
| 平台线程（两次） | 149 / 157 | 174 / 242 | 5191 / 4158 | 9532 / 8861 | 34.84 / 26.48 |
| 虚拟线程（两次） | 170 / 128 | 757 / 264 | 2921 / 2464 | 7070 / 19572 | 17.18 / 19.25 |

**p99 降低约 35%~44%，p99/p50 从 26~35 降到 17~19。**
吞吐两者接近（1108 vs 1088 req/s），因为都受外部 embedding 接口限制
（压测期间该接口返回 195 次 `GOAWAY`，属服务端连接回收策略，非本项目可控）。
瓶颈不在线程模型，尾延迟差异正是线程池排队的表现：平台线程池上限 200，
400 并发下一半请求排队；虚拟线程不排队。

收益场景是「大量并发 + 阻塞等待下游」，而非「请求路径短、不阻塞」的高吞吐接口。

## 4. 瓶颈分析

1. **同步版瓶颈是数据库行锁**：突发与售罄场景延迟接近（A 轮 212.5 vs 206.2 ms），
   说明无论库存是否充足，每个请求都要走一次数据库条件更新并竞争同一行，
   耗时由行锁排队决定。加连接池对照实验证明瓶颈不是连接池。
2. **异步版瓶颈在客户端建连速率**：400 并发 1s 爬坡两版 QPS 都落在 430~480，
   而售罄场景异步版能跑到 2,464 QPS。验证：800 并发 1s 爬坡报 692 个
   `ConnectException`；同 800 并发改 5s 爬坡全部成功。上限不在服务端。
3. **异步架构的收益来自把无效流量挡在数据库之外**：售罄请求在 Redis 里被 Lua
   脚本拦下（读库存键为 0 直接返回），不进数据库，这是 2.7 倍差距的直接来源。
4. **异步版的代价在轮询链路**：POST 路径缩短的只是建单事务，用户拿到最终
   结果要多付一次 `/{id}/result` 轮询（全链路 490→861 ms，反而变慢）。
   入口吞吐与售罄 P99 是真实收益，端到端延迟必须在面试中如实说明。

## 5. 局限

- 压测客户端与被测应用同机，共享 32 核 CPU 与网络栈，绝对值不可外推
- 中间件均为单机 Docker 容器，未测集群与故障转移
- 客户端建连速率封顶约 400 连接/秒（A 轮）/ 1,700 QPS（B 轮 T3），
  突发档位的 QPS 反映的是客户端能力
- 未测消费者积压：异步版订单创建在消费端，压测期间未观察 RocketMQ 堆积深度
- 正确性核对在压测结束后进行，未验证压测过程中的瞬时不一致
- A 轮报告与数据表完整保留，但原始 `.jtl` 未随仓库保留，无法逐条复算；B 轮全部原始数据在库可查
