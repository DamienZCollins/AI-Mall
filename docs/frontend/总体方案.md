# Mall 前端总体方案

> 以现有后端能力为边界，将 `frontend/原型.html` 的视觉与交互原型拆分为可实现的页面、组件、数据流和开发阶段。
>
> 当前只制定方案，不创建前端工程，不实现页面。

## 1. 项目定位

前端不是完整电商平台，而是后端两个核心能力的展示与操作入口：

1. **AI 混合搜索**
   - 用户可以用自然语言描述需求。
   - 前台展示搜索召回结果和商品详情。

2. **高并发秒杀**
   - 用户查看进行中的活动、发起抢购、轮询结果、进入订单和模拟支付。
   - 前台明确区分“请求已受理”和“订单创建成功”。

3. **基础商城展示**
   - 首页、商品列表、商品详情、登录与用户信息。
   - 这些页面用于承载搜索和秒杀，不扩展成完整交易平台。

### 1.1 原型定位

`frontend/原型.html` 是视觉与交互母版，不是现有后端接口清单。

| 原型内容 | 处理方式 |
| --- | --- |
| 品牌首页、商品卡片、分类导航、搜索框、响应式布局 | 保留为设计基准 |
| 商品列表、商品详情、搜索结果 | 复用首页卡片与布局，接入真实接口 |
| 秒杀活动与抢购结果 | 新增用户侧秒杀页面，沿用原型的视觉语言 |
| 登录、账户、订单 | 新增轻量页面，不照搬原型中的占位链接 |
| 购物车、收藏、会员价、普通订单、收货地址、客服 | 当前后端未提供，暂不接入 |

### 1.2 需要先确认的现实约束

- 后端没有分类字典接口，原型中的“数码、家居、个护、服饰”等分类只能作为展示文案，不能直接转换为真实分类筛选。
- 后端没有购物车、收藏和会员价格接口，原型的“加入购物车”“收藏”“会员价”不能作为首期验收项。
- 后端没有普通商品下单、收货地址和支付接口，原型中的购物车结算链路暂不落地。
- 后端只有秒杀订单的查询和模拟支付接口，订单页面首期只展示秒杀订单。
- 搜索结果使用 `productId`，商品接口使用 `id`，前端不能混用字段。
- 首页原型使用远程字体和 Unsplash 图片，正式开发时需要处理网络依赖、离线预览和加载失败兜底。

## 2. 范围与不做项

### 2.1 首期范围

- 公共布局：页头、导航、搜索入口、移动端底部导航、页脚、Toast。
- 首页：品牌展示、商品精选区、搜索入口。
- 商品列表：分页、关键字、分类 ID 过滤。
- 商品详情：真实商品字段、图片、库存、上下架状态。
- AI 搜索：自然语言关键词、分页、结果列表。
- 秒杀活动列表与详情：活动时间、价格、剩余库存、状态。
- 秒杀抢购：登录校验、抢购请求、结果轮询、成功或失败反馈。
- 秒杀订单：订单详情、待支付倒计时、模拟支付。
- 登录：账号密码登录、令牌保存、当前用户查询。
- 管理端商品：新增、编辑、上下架、图片上传。
- 管理端秒杀：活动列表、创建、编辑。

### 2.2 明确不做

- 购物车与结算
- 收藏夹
- 会员体系与会员价
- 收货地址
- 普通商品订单
- 商品评价
- 复杂分类树
- 客服系统
- 真实支付渠道

这些功能可以在后续后端补齐后再进入前端范围，首期不以静态假数据伪装成已完成功能。

## 3. 技术选型

### 3.1 建议选型

| 类别 | 建议选型 | 说明 |
| --- | --- | --- |
| 构建工具 | Vite | 启动快，配置简单 |
| 框架 | Vue 3 + TypeScript | 适合页面、组件和类型约束 |
| 路由 | Vue Router | 用户侧与管理端路由分离 |
| 状态管理 | Pinia | 只放登录态、用户信息和跨页面轻量状态 |
| HTTP | Axios 或 fetch 封装 | 统一处理令牌、错误码和超时 |
| 样式 | 原生 CSS + CSS Variables | 原型已使用变量和原生 CSS，优先沿用 |
| 组件库 | 不强制引入 | 先保留原型视觉，避免组件库风格覆盖品牌设计 |
| 测试 | Vitest + Playwright | 单元测试与关键流程浏览器验收 |
| 类型同步 | OpenAPI 生成工具 | 从 `/v3/api-docs` 生成接口类型或客户端 |

### 3.2 选择理由

- 原型是原生 HTML/CSS/JavaScript，Vue 组件化可以直接复用其设计令牌和布局逻辑。
- 页面数量以展示和表单为主，不需要为了复杂度引入重型状态框架。
- 后端已有 springdoc-openapi，前端可以从 OpenAPI 生成类型，减少手写字段错误。
- 秒杀轮询、倒计时、表单校验和错误反馈需要明确的组件边界，不能全部塞在页面里。

### 3.3 不采用的方案

- 不直接把 126 KB 的单文件原型改成生产代码：可读性、复用和测试都会变差。
- 不首期引入完整 UI 组件库覆盖原型视觉。
- 不为尚未存在的购物车、收藏和普通订单创建假接口层。
- 不把令牌、用户信息和秒杀轮询状态都塞进一个全局对象。

## 4. 信息架构与路由

### 4.1 用户侧路由

| 路由 | 页面 | 权限 | 主要接口 |
| --- | --- | --- | --- |
| `/` | 首页 | 公开 | `GET /api/products` |
| `/products` | 商品列表 | 公开 | `GET /api/products` |
| `/products/:id` | 商品详情 | 公开 | `GET /api/products/{id}` |
| `/search` | 搜索结果 | 公开 | `GET /api/search` |
| `/seckill` | 秒杀活动列表 | 公开 | `GET /api/seckill/activities` |
| `/seckill/:activityId` | 秒杀活动详情 | 公开 | `GET /api/seckill/activities/{activityId}` |
| `/seckill/:activityId/result` | 抢购结果 | 登录 | `GET /api/seckill/{activityId}/result` |
| `/orders/:orderNo` | 秒杀订单详情 | 登录 | `GET /api/seckill/orders/{orderNo}` |
| `/login` | 登录 | 公开 | `POST /api/auth/login` |
| `/me` | 当前用户 | 登录 | `GET /api/auth/me` |

### 4.2 管理端路由

| 路由 | 页面 | 权限 | 主要接口 |
| --- | --- | --- | --- |
| `/admin` | 管理端入口 | ADMIN | `GET /api/auth/me` |
| `/admin/products` | 商品管理 | ADMIN | `GET /api/admin/products` |
| `/admin/products/new` | 新增商品 | ADMIN | `POST /api/admin/products` |
| `/admin/products/:id/edit` | 编辑商品 | ADMIN | `PUT /api/admin/products/{id}` |
| `/admin/seckill` | 秒杀活动管理 | ADMIN | `GET /api/admin/seckill/activities` |
| `/admin/seckill/new` | 创建活动 | ADMIN | `POST /api/admin/seckill/activities` |
| `/admin/seckill/:id/edit` | 编辑活动 | ADMIN | `PUT /api/admin/seckill/activities/{id}` |

### 4.3 路由守卫

- 普通登录页面：未登录访问时跳转 `/login`，登录成功后回到原路径。
- 管理端页面：除登录外还需要 `role === "ADMIN"`，否则显示无权限页面。
- 公开页面：不强制登录；抢购按钮在点击时再校验登录。
- 路由参数为 ID 时统一校验为正整数，参数非法时显示 404 或回到列表。

## 5. 页面方案

### 5.1 首页

保留原型中的品牌视觉和响应式布局，替换硬编码商品数据：

- 页头：品牌、主导航、搜索框、登录入口、购物车入口。
- Hero：保留静态品牌内容，不强行绑定后端字段。
- 分类快捷入口：首期作为视觉分类或前端静态链接；没有后端分类字典时不伪造分类接口。
- 本周精选：使用 `GET /api/products?page=1&size=8` 渲染真实商品。
- 人气好物：可复用同一商品接口分页结果；不再从 HTML 中逐卡片硬编码。
- 商品卡片：名称、品牌、卖点、价格、库存、图片、状态。
- 页脚：保留品牌文案，移除或标注暂无后端的占位入口。

首页的远程图片和字体：

- 首期允许使用远程占位图，但必须处理加载失败。
- 商品真实图片使用后端返回的 `imageUrl`。
- 正式验收建议将字体和关键视觉素材本地化，避免离线环境首屏退化。

### 5.2 商品列表与详情

商品列表：

- 支持 `page`、`size`、`keyword`、`categoryId`。
- 用户侧只展示上架商品，分页信息来自统一分页结构。
- 列表为空、加载失败、请求超时要有独立状态。

商品详情：

- 使用 `GET /api/products/{id}`。
- 展示名称、品牌、描述、卖点、价格、库存、图片。
- 下架或不存在的商品按业务码 `2001` 显示“商品不可用”。
- 进入秒杀活动时使用商品 ID 关联活动，不自行拼接价格和库存。

### 5.3 AI 搜索

搜索输入：

- 顶部搜索框和首页搜索框共用同一套搜索组件。
- 提交后路由跳转到 `/search?keyword=...`，不把搜索逻辑绑在首页组件里。
- `keyword` 必填，最大 128 字符。

搜索结果：

- 调用 `GET /api/search`。
- 结果主键读取 `productId`，跳转 `/products/:productId`。
- 展示 `name`、`brand`、`sellingPoint`、`price`、`stock`、`imageUrl`。
- `score` 仅用于调试或排序观察，不作为用户可见评分。
- 分页参数最大 `size` 为 50。

搜索失败：

- 业务码 `3001` 显示“语义检索暂不可用”。
- 业务码 `3002` 显示“搜索服务暂不可用”，允许用户重试。
- 网络错误与业务错误必须区分展示。

### 5.4 秒杀活动

活动列表：

- 调用 `GET /api/seckill/activities`。
- 支持分页和 `runningOnly` 筛选。
- 展示活动标题、商品 ID、秒杀价、原价、活动时间、剩余库存、活动状态。
- 倒计时只负责展示，不依赖浏览器时间作为业务真相。

活动详情：

- 使用 `GET /api/seckill/activities/{activityId}`。
- 活动未开始、进行中、已结束、已关闭分别显示不同操作状态。
- 只有进行中且库存大于 0 时展示可点击抢购按钮。

### 5.5 抢购流程

这是前端最重要的业务闭环，必须按状态机实现，不能只写一次请求。

```text
点击抢购
  → 检查登录
  → POST /api/seckill/{activityId}
  → code === 0 只代表已受理
  → 跳转或切换到结果页
  → 轮询 GET /api/seckill/{activityId}/result
  → QUEUING：继续轮询
  → SUCCESS：停止轮询，读取 orderNo，进入订单详情或支付
  → FAILED：停止轮询，展示未抢到
```

轮询策略：

- 需要设置可取消的定时器。
- 页面离开、组件卸载、用户主动取消时停止轮询。
- 后端没有规定固定轮询次数和最大时长，前端应设置页面级超时。
- 超时后显示“仍在处理中”，允许用户重新查询结果，不要伪造失败。
- 同一页面不能同时启动多个轮询任务。

### 5.6 秒杀订单

订单详情：

- 使用 `GET /api/seckill/orders/{orderNo}`。
- 展示订单号、商品名称、成交价、订单状态、支付截止时间、支付时间。
- 状态为待支付时显示倒计时和支付按钮。
- 状态为已支付、已取消、超时取消时显示终态，不再显示支付按钮。

模拟支付：

- 使用 `POST /api/seckill/orders/{orderNo}/pay`。
- 成功后重新读取订单或使用响应中的订单数据更新页面。
- 订单状态不允许操作时按 `4007` 提示，不反复点击重试。

## 6. 数据流与前端分层

### 6.1 分层

```text
page
  ↓
feature component / composable
  ↓
api module
  ↓
http client
  ↓
backend REST API
```

| 层 | 职责 | 示例 |
| --- | --- | --- |
| `pages` | 路由页面和页面级状态 | 商品列表、秒杀详情 |
| `features` | 业务组件和业务逻辑 | 抢购轮询、活动倒计时 |
| `components` | 可复用展示组件 | 商品卡片、价格、分页、Toast |
| `api` | 接口函数与 DTO 类型 | 商品、搜索、秒杀、认证 |
| `stores` | 跨页面轻量状态 | 登录用户、令牌 |
| `router` | 路由与权限守卫 | 用户侧、管理端 |
| `styles` | 设计令牌和全局样式 | 颜色、字体、间距、断点 |

### 6.2 状态边界

- 登录态、当前用户、令牌：Pinia。
- 页面数据、分页、筛选条件：页面或组合式函数。
- 抢购轮询定时器：秒杀 feature 内部，不放入全局 store。
- 表单值、校验错误：表单组件或页面。
- Toast、弹窗：全局 UI 服务或轻量 composable。

### 6.3 HTTP 客户端

所有请求统一经过一个 HTTP 客户端：

- 拼接 Base URL。
- 自动附加 `Authorization: Bearer <token>`。
- 处理 HTTP `401`：清理登录态并跳转登录。
- 处理 HTTP `403`：显示无权限。
- 解析统一响应结构。
- 业务码非零时抛出可识别错误，页面只处理业务含义。
- 统一处理请求超时、网络错误和取消请求。
- 图片上传使用 `multipart/form-data`，字段名为 `file`。

业务错误不能全部当作“网络失败”，尤其是：

- `4004`：已售罄
- `4005`：同一活动限购
- `4009`：秒杀价不合法
- `4010`：排队服务暂不可用
- `4011`：抢购请求处理中

## 7. 工程结构

建议正式开发时采用以下结构，具体目录名可以在初始化工程时再确定：

```text
frontend/
├── src/
│   ├── api/                 # 接口函数与 DTO 类型
│   ├── assets/              # 本地图片、字体和静态资源
│   ├── components/          # 可复用展示组件
│   ├── composables/         # 请求、轮询、倒计时等组合逻辑
│   ├── features/            # 商品、搜索、秒杀、认证等业务模块
│   ├── layouts/             # 用户侧与管理端布局
│   ├── pages/               # 路由页面
│   ├── router/              # 路由与权限守卫
│   ├── stores/              # Pinia 状态
│   ├── styles/              # 设计令牌和全局样式
│   ├── types/               # 跨模块类型
│   └── main.ts
├── public/                  # 公共静态文件
├── tests/                   # 单元与端到端测试
├── docs/                    # 前端本地文档，不进入版本库
├── 原型.html                # 视觉基线，保留到生产页面迁移完成
└── README.md                # 暂不在本方案中编写
```

模块边界按业务划分，不按“所有组件放一个目录”的方式组织：

- `features/product`
- `features/search`
- `features/seckill`
- `features/auth`
- `features/admin`

## 8. 设计系统落地

原型已有较完整的设计令牌，正式开发时应先抽出，再写页面：

| 类别 | 原型来源 | 落地方式 |
| --- | --- | --- |
| 颜色 | `--paper`、`--ink`、`--persimmon`、`--sage` | 全局 CSS Variables |
| 字体 | Instrument Sans、Noto Sans SC | 本地字体或明确远程加载策略 |
| 间距 | `--gutter`、容器宽度、断点 | 布局令牌 |
| 圆角 | `--radius-s/m/l` | 组件样式令牌 |
| 动效 | `--ease`、`--fast`、`--normal`、`--slow` | 全局动画变量 |
| 响应式 | 1280 / 1100 / 860 / 600 / 370 | 统一断点 |
| 可访问性 | `focus-visible`、`sr-only`、减少动效、强制颜色 | 组件验收项 |

设计原则：

- 保留原型“纸张、墨色、柿子红”的品牌方向。
- 不把表单、表格和管理端做成与用户侧完全无关的另一套视觉。
- 状态颜色必须与品牌色协调，售罄、失败、超时不能只靠颜色表达。
- 首屏、列表、详情和管理端都要支持移动端。

## 9. 开发阶段

### 阶段 0：原型审计与接口对齐

目标：确认原型中哪些视觉和交互可以复用，哪些需要后端新增能力。

任务：

- 盘点原型页面、组件、断点和交互。
- 对照 `docs/接口文档.md` 建立页面与接口映射。
- 标记购物车、收藏、会员、地址、普通订单为暂不实现。
- 确认图片、字体和静态资源的本地化策略。

验收：

- 每个首期页面都有明确接口或明确的静态归属。
- 没有把不存在的后端接口写成假需求。

### 阶段 1：前端工程与设计令牌

目标：建立可启动、可检查的最小工程。

任务：

- 初始化 Vite + Vue 3 + TypeScript。
- 配置 ESLint、格式化、路径别名和环境变量。
- 建立全局样式、设计令牌、字体和图片资源策略。
- 搭建用户侧与管理端布局骨架。
- 建立 HTTP 客户端、统一错误类型和登录态存储。

验收：

- 开发服务器可启动。
- 页面在桌面和移动端可正常渲染。
- 设计令牌与原型一致。
- 类型检查和构建通过。

### 阶段 2：认证与基础商品

目标：完成登录、当前用户、商品列表和商品详情。

任务：

- `/login` 页面与表单校验。
- 保存令牌，刷新页面恢复登录态。
- 路由守卫与 401 处理。
- 商品列表分页、关键字、分类 ID 查询。
- 商品详情和下架商品错误处理。
- 商品卡片、价格、库存、状态、分页和空状态组件。

验收：

- 登录成功后能读取当前用户。
- 未登录访问秒杀操作时跳转登录。
- 商品列表分页正确。

## 10. 接口与页面映射

| 页面或能力 | 接口 | 前端重点 |
| --- | --- | --- |
| 登录 | `POST /api/auth/login` | 令牌、过期、错误码 1001 |
| 当前用户 | `GET /api/auth/me` | 登录态恢复、角色判断 |
| 商品列表 | `GET /api/products` | 分页、关键字、分类 ID |
| 商品详情 | `GET /api/products/{id}` | 下架和不存在 |
| 搜索 | `GET /api/search` | `productId`、分页、服务错误 |
| 秒杀列表 | `GET /api/seckill/activities` | `runningOnly`、状态、时间 |
| 秒杀详情 | `GET /api/seckill/activities/{id}` | 操作按钮条件 |
| 抢购 | `POST /api/seckill/{id}` | 只代表受理，不代表成功 |
| 抢购结果 | `GET /api/seckill/{id}/result` | 轮询状态机 |
| 秒杀订单 | `GET /api/seckill/orders/{orderNo}` | 状态和支付截止时间 |
| 模拟支付 | `POST /api/seckill/orders/{orderNo}/pay` | 状态机与重复支付 |
| 管理商品 | `/api/admin/products` | ADMIN 权限、表单、图片 |
| 管理秒杀 | `/api/admin/seckill/activities` | ADMIN 权限、时间与价格校验 |

## 11. 验收标准

### 功能

- 公开页面不登录也能浏览。
- 登录、令牌恢复、退出登录可用。
- 商品列表和详情来自真实接口。
- AI 搜索来自真实混合搜索接口。
- 秒杀抢购完整经过受理、排队、成功或失败。
- 秒杀订单能查看并模拟支付。
- 管理端只对 ADMIN 开放。

### 交互

- 所有请求都有加载、成功、空、失败状态。
- 所有按钮都有禁用和重复提交保护。
- 秒杀轮询在页面离开时停止。
- 业务错误和网络错误文案不同。
- 键盘可完成主要操作。
- `prefers-reduced-motion` 生效。

### 工程

- TypeScript 类型检查通过。
- 构建通过。
- 关键页面没有运行时控制台错误。
- 至少有一个可重复执行的端到端验收脚本。
- 页面与接口字段以 `docs/接口文档.md` 和 OpenAPI 为准。

## 12. 风险与待确认事项

| 事项 | 影响 | 处理建议 |
| --- | --- | --- |
| 原型是单 HTML 文件 | 直接改会造成不可维护 | 先抽取设计令牌和组件，再迁移页面 |
| 原型分类与后端分类 ID 不一致 | 无法做真实分类筛选 | 先确认分类字典，或首期隐藏分类筛选 |
| 购物车、收藏、会员没有后端 | 无法完成原型全部交互 | 首期标注为未接入，不伪造接口 |
| 原型使用远程字体和图片 | 离线和弱网体验不稳定 | 本地化关键资源，图片加载失败兜底 |
| 秒杀结果是异步的 | 用户容易误以为请求返回即成功 | 强制实现状态机和轮询提示 |
| 订单查询接口未校验归属 | 前端不能据此做用户级安全保证 | 需要后端后续修正，前端不隐藏该风险 |
| 管理端图片上传依赖 RustFS | 本地未启动时上传会失败 | 页面必须展示明确的基础设施错误 |
