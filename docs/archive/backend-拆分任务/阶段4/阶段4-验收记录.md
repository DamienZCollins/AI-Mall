## 2. 数据库约束

三个约束是防超卖与防重复的落脚点，都实测生效：

```sql
-- 库存非负
CONSTRAINT `ck_seckill_stock_non_negative` CHECK (`stock` >= 0)
-- 实测写入负值：ERROR 3819 (HY000): Check constraint 'ck_seckill_stock_non_negative' is violated.

-- 同一用户同一活动唯一
UNIQUE KEY `uk_user_activity` (`user_id`, `activity_id`)
```

约束设计的取向是「让数据库兜底」：应用层写错 SQL 或漏了判断，约束会直接报错而不是静默写坏数据。

## 3. 验收结果

`scripts/checks/seckill_check.py` 共 29 项，全部通过。

### 3.1 活动与时间校验

| 场景 | 结果 |
| --- | --- |
| 创建进行中的活动 | 状态 1，剩余库存 = 活动总量 |
| 秒杀价高于商品原价 | `{"code":4009,"message":"秒杀价必须低于商品原价"}` |
| 结束时间早于开始时间 | `{"code":4008,"message":"结束时间必须晚于开始时间"}` |
| 未开始的活动（状态 0）下单 | `{"code":4002,"message":"秒杀活动尚未开始"}` |
| 已结束的活动（状态 2）下单 | `{"code":4003,"message":"秒杀活动已结束"}` |
| 不存在的活动 | `{"code":4001,"message":"秒杀活动不存在"}` |
| 未登录下单 | HTTP 401 |
| USER 角色访问管理端 | HTTP 403 |
| 游客查进行中活动 | 只返回进行中的，未开始的被过滤 |

活动状态由「当前时间 + 时间窗口」推导，不落库，避免状态字段与时间不一致。

### 3.2 防重复下单：同一用户 20 并发

```text
成功 1 次，重复下单被拒 19 次
数据库订单数：1 条
库存：10 → 9（只扣 1 件）
```

同一用户 20 个并发请求同时打到接口，唯一索引 `uk_user_activity` 最终只放行 1 条插入，其余 19 次插入触发 `DuplicateKeyException`，被转换为业务错误码 4005。整个过程没有先查后插的竞态窗口。

### 3.3 防超卖：10 库存 / 20 用户并发

```text
成功下单：10 次
被拒售罄：10 次
其它响应：无
剩余库存：0
数据库订单数：10 条
```

库存扣减用的是条件更新：

```sql
UPDATE seckill_stock SET stock = stock - 1 WHERE activity_id = ? AND stock > 0
```

`WHERE stock > 0` 由 InnoDB 行锁串行化，20 个并发请求里恰好 10 个影响行数为 1，另外 10 个影响行数为 0 并抛出货架售罄，订单插入随事务一起回滚。成功数、订单数、库存余量三者自洽。

售罄后用未下过单的新用户再请求，返回 `{"code":4004,"message":"秒杀商品已售罄"}`。

### 3.4 订单状态机

| 场景 | 结果 |
| --- | --- |
| 待支付订单支付 | 成功，状态变为 2 已支付 |
| 已支付订单再次支付 | `{"code":4007,"message":"当前状态为「已支付」，不能支付"}` |
| 已支付订单过期 | 不会被超时任务取消，状态保持 2 |
| 已支付订单的库存 | 不回补，保持 9 |

状态流转同样走条件更新 `WHERE order_no = ? AND status = ?`，只有处于源状态才能流转，终态订单无法被改回。

### 3.5 超时取消与库存回补

```text
下单成功 orderNo=SK202610021738011154
库存：5 → 4
把 expire_time 提前 1 分钟，等待定时任务扫描
订单状态：2 待支付 → 4 超时取消
库存：4 → 5（已回补）
再等一轮扫描，库存仍为 5（未重复回补）
回补后可再次下单成功
```

回补不重复靠的是条件更新的影响行数：超时任务先执行
`UPDATE seckill_order SET status = 4 WHERE order_no = ? AND status = 1`，
只有影响行数为 1 才执行库存回补。任务重复跑第二次时影响行数为 0，直接跳过。
回补语句本身还有上限保护 `WHERE stock < total_stock`，异常情况下不会把库存撑过活动总量。

## 4. 关键设计取舍

### 4.1 为什么先插订单再扣库存

反过来先扣库存的话，重复下单被唯一索引拦下时库存已经扣掉，回滚虽然能纠正，但如果扣减与插入不在同一事务（后续改成异步时很容易发生），就会出现「白扣」。先插订单让唯一索引尽早拦截，扣库存只对确定能成立的请求执行，语义上更干净。

### 4.2 为什么用条件更新而不是乐观锁版本号

`UPDATE ... WHERE stock > 0` 一步完成了「判断 + 修改」，中间没有暴露给其它事务的窗口。若改成「先 SELECT 读出 stock、判断、再 UPDATE 带版本号」，判断与修改之间需要额外处理版本冲突，代码和失败分支都更多，而收益相同。

### 4.3 为什么活动状态不落库

状态与时间窗口是同一份事实的两种表示，落库就必然面临两者不一致（比如定时任务没跑、时钟漂移）。由 `start_time` / `end_time` 与当前时间推导，只有一个数据源，不会出现「时间已过但状态还写着进行中」。

### 4.4 为什么用定时任务而不是延迟消息

阶段 4 的目标是把业务与约束做正确，RocketMQ 延迟消息属于性能与精确性的优化。定时任务有 1 分钟量级的延迟，但语义正确、无额外依赖。阶段 5 会改用延迟消息做精确触发，这个任务保留作兜底。

## 5. 过程中的问题

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 售罄断言取错用户 | 售罄用例复用了已下过单的用户，返回 4005 而非 4004，断言失败 | 不是代码缺陷：唯一索引先于库存判断拦截，是合理顺序。改用全新用户验证售罄分支，并说明两者优先级 |

## 6. 已知事项

- **并发规模有限**：验证用的是 20 并发，能暴露约束层面的问题，但不代表高并发下的表现。阶段 6 会用 JMeter 加压。
- **超时取消有分钟级延迟**：定时任务 60 秒一轮，超时订单最长会晚 1 分钟才被取消。阶段 5 用延迟消息解决。
- **支付未校验归属**：`/api/seckill/orders/{orderNo}/pay` 只认订单号，任何登录用户都能支付他人订单。当前是模拟回调，真实场景应由支付网关回调和签名保证。
- **下单链路是同步串行的**：请求要等 MySQL 事务提交才返回，库存扣减持有行锁。这是阶段 5 要解决的主要瓶颈。
- **`pay_timeout_minutes` 最小为 1 分钟**：验收时需要等待定时任务周期，实际约 3 分钟。
- **没有取消订单接口**：状态机支持「待支付 → 已取消」，但未开放主动取消接口，阶段 4 只需要超时这一条路径。
