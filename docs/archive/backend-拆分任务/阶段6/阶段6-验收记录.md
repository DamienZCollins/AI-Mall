# 阶段 6 验收记录（A 轮）

> 记录时间：2026-10-14
> 目标：用真实压测数据量化异步秒杀相对同步版本的收益，并定位瓶颈。
> 注：本记录为 A 轮数据；2026-10-20 以 200 线程统一复跑了 B 轮（原始 `.jtl` 在
> `backend/scripts/loadtest/results/` 可复算），两轮已合并进 `docs/压测报告.md`。
> 对外口径（简历）使用 B 轮：T3 吞吐 671→1,829 QPS（2.7×），P99 472→217 ms（−54%）。

## 1. 结论

**售罄后流量场景下，异步版本吞吐是同步版本的 2.76 倍（2464.1 vs 891.3 QPS），
P99 从 339 ms 降到 157 ms。**

突发抢购场景两者 QPS 相当（受客户端建连速率限制），但异步版本平均延迟低 47%。

两个版本在全部档位下均无超卖、无重复下单，库存守恒。

## 4. 过程中发现的问题

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| `boolProp` 不支持属性替换 | `${__P(keepalive,true)}` 被当作 false，keep-alive 始终关闭，每请求新建连接 | JMeter 的 `<boolProp>` 节点只认字面值，改为写字面 `true`；`scheduler` 同样受影响 |
| keep-alive 关闭导致端口耗尽 | 2 万多个 TIME_WAIT，报 `SocketException` 与 `BindException`，错误率 51%~74% | 修正 keep-alive 后错误归零。这类错误发生在客户端建连阶段，服务端日志干净 |
| HttpClient4 建连速率低 | 同样 200 并发，HttpClient4 报 47.5% SocketException，Java 实现零错误 | 改用 `HTTPSampler.implementation=Java` |
| 单循环压测测的是爬坡 | 线程数等于样本数，QPS 等于线程数除以爬坡时间，与系统能力无关 | 持续压测改用 `loops=-1` + 调度器 |
| 调度器未生效 | `duration=5` 实际跑了 60 秒不停 | `continue_forever` 与 `scheduler` 同为 boolProp，只能写字面值 |
| 预热开销污染延迟 | 异步版本平均延迟 1601 ms，远高于同步版本 | 预热在首个请求路径上同步执行；压测前先触发预热并还原库存与订单，延迟降到 101 ms |
| 残留 JMeter 进程 | TIME_WAIT 长时间不下降，端口始终紧张 | 上一轮被中断的 JMeter 进程仍在打请求，杀掉后 TIME_WAIT 从 23651 降到 140 |
| 响应体未写入 JTL | 无法统计业务码分布 | `response_data` 列需在 JMX 层配置，本次改用断言与响应字节数区分结果 |
| 相对路径解析 | CSV 路径按 JMX 所在目录解析，报 `File tokens.csv must exist` | 传绝对路径 |
| 虚拟线程被 `synchronized` 钉住 | 生产者构造含网络 I/O，Java 21 下会阻塞载体线程调度 | 改用 `ReentrantLock`（JEP 491 到 Java 24 才修此问题） |
| 外部 embedding 接口限流 | 400 并发搜索压测报 195 次 `GOAWAY`，业务失败率 94% | 外部服务连接回收策略，非本项目可控；已在报告中标注为对照实验的干扰因素 |

虚拟线程对照实验（秒杀无收益、搜索 p99 降 35%~44%）数据见 `docs/压测报告.md` 3.4 节。

## 5. 瓶颈结论

1. **同步版本瓶颈是数据库行锁**：突发与售罄场景延迟接近（212.5 vs 206.2 ms），
   说明每个请求无论库存是否充足都要竞争同一行，耗时由锁排队决定。
2. **异步版本瓶颈在客户端建连速率**：400 并发突发档位 QPS 落在 430~480，
   而售罄档位能跑到 2464 QPS。对照实验证实——800 并发 1 秒爬坡报 692 个
   `ConnectException`，同样 800 并发改 5 秒爬坡则全部成功。
3. **异步架构的收益来自把无效流量挡在数据库外**：售罄请求在 Redis 层被拦下，
   不进数据库，这是 2.76 倍差距的直接来源。

## 6. 局限

- 压测客户端与被测应用同机，共享 CPU 与网络栈，绝对值不可外推
- 中间件均为单机 Docker 容器，未测集群与故障转移
- 客户端建连速率封顶约 400 连接/秒，突发档位反映的是客户端能力
- 未测消费者积压：压测期间未观察 RocketMQ 的堆积深度
- 正确性核对在压测结束后进行，未验证压测过程中的瞬时一致性
