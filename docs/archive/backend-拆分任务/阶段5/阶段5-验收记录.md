# 阶段 5 验收记录

> 记录时间：2026-10-02
> 环境：Windows + Java 21（Liberica 21.0.4）+ Spring Boot 3.5.16
> 依赖：MySQL 8.4、Redis 7.2、RocketMQ 5.3.2（gRPC 代理接入）

## 1. 架构变化

阶段 4 的下单是「请求 → MySQL 事务」，库存扣减持有行锁，请求要等事务提交才返回。
阶段 5 把链路改成两级：

```text
请求 → Redis Lua 原子预扣 → 投递 MQ → 立即返回
                                    ↓
                            消费端异步落库 + 扣减 MySQL 库存
                                    ↓
                            投递延迟消息 → 到期关单并回补
```

Redis 承担抢购流量的判断与扣减，MySQL 只做最终落库。阶段 4 的数据库约束全部保留：
唯一索引 `uk_user_activity`、条件更新 `stock > 0`、`CHECK (stock >= 0)` 仍是最后一道防线。

## 3. 验收结果

`scripts/checks/seckill_async_check.py` 共 33 项，全部通过。

### 3.1 库存预热

| 场景 | 结果 |
| --- | --- |
| 创建活动后 | Redis 库存键 = 活动总量，买家集合键已建立 |
| 应用重启后 | 启动时预热未结束的活动，进行中的活动仍可下单 |
| Redis 键被淘汰 | 下单时按需预热，不因缓存丢失拒绝请求 |

### 3.2 抢购与轮询

```text
POST /api/seckill/{id}  ->  {"code":0}           立即返回
Redis 库存              ->  10 → 9
GET  /{id}/result       ->  {"state":"QUEUING"}  → 轮询
                        ->  {"state":"SUCCESS","orderNo":"SK202610021809436895",...}
数据库                  ->  订单已落库，库存 10 → 9
```

同一用户重复抢购返回 `{"code":4005,"message":"同一活动每人限购一件"}`，
由 Redis 买家集合拦截，不进数据库。

### 3.3 并发防超卖：10 库存 / 20 用户同时请求

```text
进入排队：10    售罄被拒：10    其它响应：无
Redis 库存：0
异步落库订单：10 条
数据库库存：0
单用户最大订单数：1
```

20 个并发请求同时打 Lua 脚本，脚本的原子性保证只有 10 个扣减成功；
10 条消息被消费后落库 10 条订单，MySQL 库存同步扣到 0。Redis 库存、数据库库存、
订单数三者一致。

### 3.4 MQ 不可用时的降级

```text
停止代理 → POST /api/seckill/{id}
  -> {"code":4010,"message":"排队服务暂不可用，请稍后重试"}
  -> Redis 预扣已回补（库存 5 保持不变）
  -> 买家标记已移除，用户可重试
  -> 未产生订单
重启代理 → 恢复可用
```

这是「Redis 或 MQ 异常时系统不进入不可恢复状态」的实测：预扣与投递在同一处，
投递失败立即回补，不会出现「库存扣了但没有订单」的悬空状态。

### 3.5 延迟消息关单

```text
抢购成功 → Redis 库存 3 → 2 → 异步订单创建
等待 1 分钟（活动配置的超时时间）
  -> 订单状态 1 待支付 → 4 超时取消
  -> Redis 库存 2 → 3
  -> 数据库库存 2 → 3
  -> 买家标记保留（uk_user_activity 限定同一用户同一活动终身一单，
     释放的库存留给其他用户）
```

### 3.6 已支付订单不受延迟消息影响

```text
抢购 → 支付 → 订单状态 2 已支付
等待延迟消息到期
  -> 订单状态仍为 2，未被关单
  -> Redis 库存不回补
```

### 3.7 预热重建（模拟重启或 Redis 键被淘汰）

```text
用户 05 抢购成功 → 订单落库 → 数据库库存 4 扣到 3
清空该活动的全部 Redis 键（模拟应用重启或键被淘汰）
用户 05 重抢 → {"code":4005}   预热从数据库回填了买家集合，拦住
  Redis=3 数据库=3             两侧一致，没有泄漏
用户 06 重抢 → 受理 → 订单创建成功
  Redis=2 数据库=2             两笔订单后仍一致
```

预热是把活动状态从数据库**完整重建**到 Redis：库存取 `seckill_stock.stock`，
买家集合按 `seckill_order` 中该活动已有的订单行回填。

**为什么不能清空买家集合**：`uk_user_activity` 限定终身一单，已下单的用户即使订单被取消也占着资格。
清空后该用户会再次通过 Redis 预扣，消费端虽被唯一索引拦下并按幂等返回成功，
Redis 库存却已经扣掉且无人回补。实测复现：

```text
下单后            Redis=2 数据库=2
清空买家集合后重抢  响应 code=0（Redis 放行了）
结果              Redis=1 数据库=2   库存泄漏，订单数却没有增加
```

泄漏是静默的：用户看到「抢购成功」（其实是他那张旧订单），库存却少了一份，后续用户会提前遇到售罄。

## 4. 关键设计取舍

### 4.1 为什么预扣在 Redis、落库在 MySQL

抢购的瓶颈是**判断与扣减**。放在数据库里，每笔请求都要开事务、持有行锁、等提交；
放在 Redis 里，Lua 脚本一次执行完成时间校验、去重、扣减，天然串行且无锁竞争。
MySQL 退回到「记账」角色，只处理 Redis 放行的少量请求。

### 4.2 为什么消息发送失败要回补 Redis

预扣成功后如果消息没进 MQ，这笔资格就凭空消失了——用户看到抢购成功但永远等不到订单。
回补在同一段代码内完成，把「预扣 + 投递」当作一个需要补偿的整体，而不是两个独立步骤。

### 4.3 为什么消费端还要扣一次数据库库存

Redis 是热数据，可能被淘汰、被误删、被人工修改。数据库库存是最终事实，
消费端扣减成功才认为这笔交易落地。两者对不上时消费抛异常让消息重投，而不是吞掉差异。

### 4.4 为什么用条件更新而不是靠判断

超时关单、库存回补、订单状态流转全部用 `UPDATE ... WHERE 旧状态 = ?`，
影响行数为 1 才继续。这样不管消息重投几次、定时任务和延迟消息是否同时到达，
同一个订单只会被处理一次。

### 4.5 为什么普通消息和延迟消息分两个主题

RocketMQ 5.x 的每个主题都声明了能接受的消息类型（`message.type` 属性）。
同一主题无法同时接受 NORMAL 与 DELAY（`MIXED` 类型 broker 侧不支持），
发送时报 `Current message type not match with topic accept message types`。
拆成 `mall-seckill-order`(NORMAL) 与 `mall-seckill-timeout`(DELAY) 两个主题即可。

## 5. 过程中的问题

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 环境变量撞车 | `.env` 里阶段 0 的 `ROCKETMQ_TOPIC=mall-topic` 覆盖了应用配置，消费者连到了不存在的主题 | 应用改用专属变量名 `ROCKETMQ_SECKILL_ORDER_TOPIC` |
| 主题未声明消息类型 | 发送普通消息报 `message type not match`，只声明 DELAY 会拒收普通消息 | 建主题时显式声明 `message.type`，普通与延迟拆成两个主题 |
| 代理缓存主题路由 | 主题建好后客户端仍报 `No topic route info` | 新建主题后重启代理，已写进建主题脚本的提示 |
| 消费端漏扣数据库库存 | 异步订单落库了，但 MySQL 库存没减，两侧不一致 | 消费端在落库后调用条件扣减，扣不动则抛异常让消息重投 |
| 空集合不占 Redis 键 | 预热后买家集合键不存在，无法单独设置 TTL | 写入一个不会被命中的占位成员，让键真实存在并挂上过期时间 |
| 预热清空买家集合导致库存泄漏 | 重启或活动编辑触发预热后，已下单用户能再次通过 Redis 预扣；消费端被唯一索引拦下按幂等返回成功，Redis 库存却只减不还 | 预热改为从 `seckill_order` 回填买家集合而不是清空；补「重启后本人重抢被拒且两侧库存一致」的用例 |
| 代理与 broker 启动竞态 | Docker 重启后 proxy 报 `create system broadcast topic DefaultHeartBeatSyncerTopic failed` 并退出 | broker 健康检查只做 TCP 连通，早于其能响应管理请求；重启一次 proxy 即可。属环境问题，未改代码 |
| ES 解析不了自己的主机名 | Docker 重启后 ES 报 `UnknownHostException: <容器短 ID>` 并退出 | compose 为 elasticsearch 显式指定 `hostname`，与 `node.name` 保持一致 |

## 6. 已知事项

- **活动结束后买家集合仍保留**：Key 的 TTL 是活动结束时间加一天，之后自动清理。
- **回补上限校验依赖 Redis 里的总量键**：若该键被淘汰，会回查活动表取总量。
- **延迟消息的精度**：实测设定 10 秒延迟，收到时间约 12 秒，含 brokers 投递与消费轮询开销；
  关单时间不是精确到秒的，业务上可接受。
- **抢购接口不返回订单号**：订单异步创建，前端需要轮询 `/{activityId}/result`。
- **死信队列未处理**：消费重试超过上限后消息进 DLQ，当前没有补偿程序。在终身一单的规则下，
  这类用户的买家标记不会释放，会一直停在「排队中」，需要人工介入。
- **活动进行中编辑会重置 Redis 状态**：预热从数据库重建，会把在途且尚未落库的订单预扣丢掉，
  活动一旦开始就不应再编辑。
- **预热锁是单机短锁**：用 Redis `SETNX` 收敛并发预热，多实例下语义仍然正确，
  但锁的持有时间与等待上限要按实际预热耗时调整。
- **本地准入点是代理**：生产环境接入 RocketMQ 通常直连或走共享代理，`mall.rocketmq.endpoints`
  按环境配置即可，代码不变。
