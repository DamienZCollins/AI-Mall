# 阶段 4 拆分任务

> 目标：完成秒杀用户侧闭环——活动浏览、抢购受理、结果轮询、订单详情与模拟支付，全部按状态机实现。
> 状态：已完成
> 前置：阶段 2 已验收（登录态、路由守卫、HTTP 客户端）；后端阶段 4 与阶段 5 已验收（Redis 预扣 + RocketMQ 异步下单）。

## 4.1 秒杀接口封装

- [x] 新增 `src/api/seckill.ts`，六个接口逐一封装，路径与参数名照抄 `docs/接口文档.md` 第 7 章
- [x] `listActivities({ page, size, runningOnly })` → `GET /api/seckill/activities`：`page` 最小 1，`size` 1 到 100，`runningOnly` 仅在为 `true` 时拼进查询串；`getActivity(activityId)` → `GET /api/seckill/activities/{activityId}`
- [x] `placeOrder(activityId)` → `POST /api/seckill/{activityId}`，无请求体，成功时 `data` 为 `null`，返回类型声明为 `Promise<void>`
- [x] `getResult(activityId)` → `GET /api/seckill/{activityId}/result`，字段 `state`、`orderNo`、`productName`、`seckillPrice`、`status`、`expireTime`
- [x] `getOrder(orderNo)` → `GET /api/seckill/orders/{orderNo}`；`payOrder(orderNo)` → `POST /api/seckill/orders/{orderNo}/pay`，返回更新后的订单

**说明**：`POST /api/seckill/{activityId}` 返回 `code === 0` 仅表示 Redis 已受理预扣并投递了消息，订单由消费者异步创建，接口不返回订单号。

**验收**

## 4.5 抢购状态机

```text
点击「立即抢购」
  → 登录校验
      ├─ 未登录 → 跳 /login?redirect=/seckill/{activityId}，结束
      └─ 已登录 → 继续
  → POST /api/seckill/{activityId}
      ├─ code === 0 → 仅代表已受理，继续
      └─ 非零 code → 按下方错误表处理，结束
  → 跳转 /seckill/{activityId}/result（带受理标记）
  → 轮询 GET /api/seckill/{activityId}/result
      ├─ QUEUING → 继续轮询
      ├─ SUCCESS → 停止轮询，取 orderNo，进入 /orders/{orderNo}
      ├─ FAILED  → 停止轮询，展示未抢到
      └─ 轮询超时 → 停止轮询，展示「仍在处理中」，可手动重新查询
```

- [x] 抢购入口统一走 `features/seckill/useSeckillPurchase.ts`，页面不直接调 api
- [x] `code === 0` 后只跳结果页，不出现「下单成功」、不出现订单号、不出现支付按钮；跳转带受理标记，结果页据标记自动轮询
- [x] 错误分支：

| 业务码 | 含义 | 前端处理 |
| --- | --- | --- |
| `4002` | 秒杀活动尚未开始 | 提示未开始，重新拉取活动详情，按钮回到「未开始」 |
| `4003` | 秒杀活动已结束 | 提示已结束，重新拉取活动详情，按钮回到「已结束」 |
| `4004` | 秒杀商品已售罄 | 提示已售罄，重新拉取活动详情刷新库存，不当作网络故障 |
| `4005` | 同一活动每人限购一件 | 提示已达限购，提供「查看我的订单」入口，不再重试 |
| `4010` | 排队服务暂不可用 | 提示稍后重试，按钮恢复可点击，允许重新发起 |
| `4011` | 抢购请求处理中 | 提示处理中，禁止重复提交，转入结果页查询 |

**说明**：`4011` 在接口文档与后端业务码表中存在，但当前后端抢购路径未见触发，前端按「已受理待确认」处理，触发条件待联调确认。

**验收**

- [x] 受理成功后页面不出现「下单成功」「订单号」「去支付」
- [x] 六个错误码各有独立文案，`4004`、`4005` 不被展示为网络错误；未登录点击抢购跳登录，登录后回到原活动详情

## 4.6 轮询实现

- [x] 新增 `src/composables/useSeckillPolling.ts`，只负责定时器与请求节奏，不持有页面 UI 状态
- [x] 入参 `activityId`、是否自动开始、`onState` 回调；出参 `state`、`orderNo`、`running`、`start()`、`stop()`、`queryOnce()`
- [x] 间隔递增（1s → 2s → 3s → 5s，上限 5s），用常量集中定义；页面级超时 60 秒，超时后 `stop()` 并置为 `timeout`
- [x] 定时器可取消，`stop()` 后不再有在途回调写状态；`onUnmounted` 与路由离开都调用 `stop()`
- [x] 同一页面只允许一个轮询：`start()` 内部先 `stop()` 再启动，重复调用不产生第二个定时器
- [x] 单次请求失败不算 `FAILED`：按递增间隔继续或置为错误态，页面展示「查询失败，点击重试」
- [x] 超时态展示「仍在处理中」并提供「重新查询」，点击后重新 `start()`；轮询期间抢购按钮与重新查询按钮按状态禁用

**说明**：后端没有规定轮询次数与最大时长，超时是前端策略；`FAILED` 是后端明确返回的业务结果，只有它代表未抢到，超时与请求失败都不能降级成它。

**验收**

- [x] 连续点击抢购不会出现两条并行轮询；离开结果页后网络面板不再有 `/result` 请求，组件卸载无定时器泄漏
- [x] 超时后不显示「未抢到」，重新查询能恢复轮询

## 4.7 结果页 `/seckill/:activityId/result`

- [x] 新增路由，登录后可访问；未登录跳 `/login` 并带回跳路径
- [x] 三种 `state` 对应三种 UI：

| `state` | 展示 | 后续动作 |
| --- | --- | --- |
| `QUEUING` | 「正在为你排队」+ 加载态 + 已等待时长 | 继续轮询 |
| `SUCCESS` | 「抢购成功」+ `productName`、`seckillPrice`、`expireTime` | 跳 `/orders/{orderNo}`，或直接支付 |
| `FAILED` | 「很遗憾，本次未抢到」 | 返回活动详情或秒杀列表 |

- [x] `SUCCESS` 必须用 `orderNo` 跳详情，不自行拼订单号，并提示支付截止时间 `expireTime`
- [x] 直接刷新该页：无受理标记时执行一次 `queryOnce()`，不因刷新而空白
- [x] 从未参与过的用户也会拿到 `FAILED`，其文案用「未查询到抢购记录」兜底，不与「抢购失败」混用
- [x] 轮询超时态与 `QUEUING` 的 UI 分开，文案「仍在处理中」并给「重新查询」；提供「返回活动详情」与「查看我的订单」入口

**说明**：后端结果接口按「是否存在订单」与「是否在 Redis 买家集合中」区分三种 `state`，从未参与同样落到 `FAILED`，因此文案不能直接等同于「抢购失败」。

**验收**

- [x] 三种 `state` 都能正确展示，不出现空白页；刷新结果页会重新查询，不会停在加载态
- [x] `SUCCESS` 后的订单号与订单详情页一致

## 本阶段不做

- 不做真实支付渠道，只接模拟支付接口
- 不做订单列表与「我的订单」页，后端未提供按用户查询订单的接口
- 不做取消订单、退款、售后
- 不把倒计时作为抢购资格或订单状态的判定依据
- 不实现排队位次与队列进度条，后端不返回位次
- 不接入管理端秒杀活动维护，属于阶段 5
