## 1. 联调脚本与原始结果

联调脚本：`tests/e2e/record-phase4.mjs`，按「创建商品 → 上架 → 创建活动 → 抢购 → 轮询 → 订单 → 支付 → 停用」顺序调用真实接口。以下为脚本真实输出。

### 1.1 创建并上架商品

```json
{"code":0,"data":{"id":45,"name":"阶段4 联调商品 1792243960999","price":199,"stock":10,"status":0}}
{"code":0,"data":{"id":45,...,"status":1}}
```

新增后 `status=0`（下架），`PATCH` 后 `status=1`。

### 1.2 创建活动

```json
{"code":0,"data":{"id":125,"productId":45,"title":"阶段4 联调活动 1792243960999",
"seckillPrice":99,"originalPrice":199,"totalStock":3,"remainingStock":3,
"perUserLimit":1,"startTime":"2026-10-17T21:27:00","endTime":"2026-10-17T23:32:00","status":1}}
```

时间窗口覆盖当前时刻，后端推导 `status=1`（进行中）。

### 1.3 抢购受理

```json
{"code":0,"message":"成功","data":null}
```

`data` 为 `null`，不返回订单号，仅表示 Redis 已预扣库存并投递消息。

### 1.4 轮询结果

```text
6.1 轮询结果 state=SUCCESS orderNo=SK1792243963220-2-125
```

```json
{"code":0,"data":{"state":"SUCCESS","orderNo":"SK1792243963220-2-125",
"productName":"阶段4 联调商品 1792243960999","seckillPrice":99,"status":1,
"expireTime":"2026-10-17T21:47:43"}}
```

第一次轮询即拿到 `SUCCESS`（本机消费延迟约 1 秒）。`QUEUING` 分支在连续多次抢购压测中出现过，前端按「继续轮询」处理。

### 1.5 订单详情

```json
{"code":0,"data":{"orderNo":"SK1792243963220-2-125","activityId":125,"productId":45,
"productName":"阶段4 联调商品 1792243960999","seckillPrice":99,"status":1,
"expireTime":"2026-10-17T21:47:43","payTime":null}}
```

### 1.6 模拟支付

```json
{"code":0,"data":{"orderNo":"SK1792243963220-2-125",...,"status":2,"payTime":"2026-10-17T21:32:43"}}
```

支付后 `status` 由 `1` 变 `2`，`payTime` 写入。前端用该响应整体替换页面订单对象，不再发第二次 GET。

### 1.7 业务码实测

| --- | --- | --- |
| `4005` | 同一用户对同一活动再次抢购 | `{"code":4005,"message":"同一活动每人限购一件","data":null}` |

### 1.8 停用活动

```json
{"code":0,"data":{"id":125,...,"remainingStock":2,"status":3}}
```

`PUT status=0` 后活动状态变为 `3`（已关闭）。

停用后同一用户再次抢购返回的仍是 `4005`（限购）而不是 `4003`（已结束）——后端先校验买家集合再校验活动状态。前端对两个码都有独立文案，行为正确。

## 3. 状态机实测

### 3.1 抢购链路

```text
点击「立即抢购」
  → 未登录 → 跳 /login?redirect=/seckill/125，结束后登录回到原活动
  → POST /api/seckill/125 → code === 0（data=null，仅代表受理）
  → 跳 /seckill/125/result?accepted=1
  → 轮询 GET /api/seckill/125/result
      → SUCCESS → 停止轮询，读 orderNo，进 /orders/{orderNo}
```

实测：点击后地址栏变为 `/seckill/125/result?accepted=1`，页面先显示「正在为你排队」，随后切换为「抢购成功」，未出现「下单成功」、订单号或支付按钮。

### 3.2 活动状态与按钮矩阵

| `status` | 库存 | 按钮文案 | 可点击 | 实测 |
| --- | --- | --- | --- | --- |
| `0` 未开始 | 任意 | 未开始 | 否 | 文案与禁用均生效 |
| `1` 进行中 | > 0 | 立即抢购 | 是 | 实测可点击并完成抢购 |
| `1` 进行中 | `= 0` | 已售罄 | 否 | 代码分支存在，本轮库存未耗尽未实测 |
| `2` 已结束 | 任意 | 已结束 | 否 | 已有历史活动 `status=2`，页面渲染正确 |
| `3` 已关闭 | 任意 | 已关闭 | 否 | 停用后实测 `status=3` |

`resolveActionButton` 单测覆盖了全部 5 种组合（`tests/unit/seckill-labels.spec.ts`）。

### 3.3 订单状态

## 4. 轮询实现

| 检查项 | 实测结果 |
| --- | --- |
| 间隔递增 | 1s → 2s → 3s → 5s，上限 5s（`POLLING_INTERVALS`） |
| 页面级超时 | 60s（`POLLING_TIMEOUT_MS`），超时置 `timeout` 并 `stop()` |
| 定时器可取消 | `stop()` 清定时器并 abort 在途请求 |
| 单实例 | `start()` 内部先 `stop()`，重复点击不产生第二个定时器 |
| 离开页面 | `onBeforeUnmount` 与路由离开都调用 `stop()` |
| 单次请求失败 | 不置为 `FAILED`，保持轮询并继续递增间隔 |
| 超时态 | 展示「仍在处理中」+「重新查询」，不伪造成失败 |

### 4.1 轮询停止实测

从结果页离开后，Playwright 断点与网络面板确认不再有 `/result` 请求；`onBeforeUnmount` 中 `disposed = true` 后所有在途回调直接返回，不写状态。

### 4.2 轮询超时

页面级超时 60s 为前端策略，后端未规定最大时长。超时态与 `QUEUING` 的 UI 分开：`QUEUING` 是转圈 +「正在为你排队」，超时是时钟图标 +「仍在处理中」+ 重新查询按钮。

## 5. 结果页三态

| `state` | 展示 | 实测 |
| --- | --- | --- |
| `QUEUING` | 「正在为你排队」+ 加载态 + 已等待秒数 | 实测出现 |
| `SUCCESS` | 「抢购成功」+ 订单号、商品、成交价、支付截止 | 实测出现，`orderNo` 与订单详情一致 |
| `FAILED` | 「未查询到抢购记录」（有 `productName` 时为「很遗憾，本次未抢到」） | 代码分支存在，未构造 |

### 5.1 FAILED 文案

后端按「是否存在订单」与「是否在 Redis 买家集合中」区分三态，从未参与的用户同样落到 `FAILED`。前端因此用 `result.productName` 判断：无商品名时显示「未查询到抢购记录」，不与「抢购失败」混用。

### 5.2 刷新结果页

直接刷新 `/seckill/{id}/result`（无 `accepted` 标记）时先 `queryOnce()` 查询一次，不因刷新而空白；若查询到 `QUEUING` 则自动继续轮询。

## 6. 登录校验与守卫

| 场景 | 实测结果 |
| --- | --- |
| 未登录浏览 `/seckill`、`/seckill/:id` | 允许，不强制登录 |
| 未登录点击抢购 | 跳 `/login?redirect=/seckill/125`，登录后回到原活动 |
| `/seckill/:id/result`、`/orders/:orderNo` 未登录 | 路由守卫拦截，跳登录并带回跳路径 |

| 轮询中令牌失效 | HTTP 客户端统一 401 处理，`stop()` 后跳登录，不再刷请求 |

## 7. 问题与已知事项

- **订单号格式与接口文档不一致**：`docs/接口文档.md` 7.5 / 7.6 示例为 `SECKILL202610170001`，实际返回 `SK1792243963220-2-125`（`SK` + 时间戳 + 用户 ID + 活动 ID）。前端只把它当字符串透传，不解析、不拼接，因此不受影响；文档需同步修订。
- `4003`（活动已结束）与 `4002`（未开始）在本轮未构造出真实触发：停用活动后再次抢购时，后端先命中 `4005` 限购。前端对两个码均有独立文案与分支，待补测。
- 活动 `status` 不落库，由时间窗口与配置开关推导；`3`（已关闭）与 `2`（已结束）语义不同，前端分别建模。
- `remainingStock` 是后端活动库存行的剩余值，秒杀成功后减少（实测 3 → 2），前端只展示不参与判定。
- 免费/不可用的 4010 排队服务异常未触发，属后端异常路径。
- 倒计时只做展示：修改本机系统时间不会影响按钮可用性，按钮可用性完全以接口返回的 `status` 与 `remainingStock` 为准。

## 7.1 业务码可达性补测

此前 4002、4003、4004、4010 记为「未触发」，原因是前置条件没构造对，不是接口不可达。
补测为每个码构造真实前置条件后逐一验证，脚本见 `tests/e2e/record-bizcodes.mjs`、`tests/e2e/record-4010.mjs`，
并在 `tests/e2e/bizcodes.spec.ts` 固化为可重复执行的用例。

| 业务码 | 构造方式 | 真实响应 |
| --- | --- | --- |
| `4002` | 创建 `startTime` 在未来 60 分钟的活动（后端推导状态 `0`） | `{"code":4002,"message":"秒杀活动尚未开始"}` |
| `4003` | 创建起止时间都在过去的活动（后端推导状态 `2`） | `{"code":4003,"message":"秒杀活动已结束"}` |
| `4004` | 库存 1 的活动由 user 抢走后再由 admin 抢购 | `{"code":4004,"message":"秒杀商品已售罄"}` |
| `4005` | 同一用户对同一活动第二次抢购 | `{"code":4005,"message":"同一活动每人限购一件"}` |
| `4010` | 停掉 RocketMQ proxy 后抢购 | `{"code":4010,"message":"排队服务暂不可用，请稍后重试"}` |

`4010` 还验证了补偿逻辑：触发后活动 `remainingStock` 从 4 恢复到 5（与 `totalStock` 一致），
`/result` 返回 `FAILED`，说明预扣已回补、没有留下占用。

页面侧同步验证：`4002` 按钮文案为「未开始」且禁用，`4003` 为「已结束」且禁用，
`4004` 为「已售罄」且禁用。

`4011` 确认**不可达**：`ResultCode.SECKILL_QUEUING` 在整个后端仅有一处常量定义，没有任何抛出点。
前端保留其文案与分支以便后端将来启用时无需改动，但验收记录不把 `4011` 计为已验证。
